# Zelvik-Edge 26.10.4.9

本版本取代 `26.10.4.8`，补上 Mace 0.1.x 到 0.2.0 的真实迁移流程。`v26.10.4.8` 的 tag、Release 与镜像保持不变。

## 为什么需要本版本

`26.10.4.8` 使用 Mace 0.2.0（btree 格式 2），启动时无法打开 `26.10.4.7` 及更早版本写入的 `data/metrics.mace`、`data/telemetry/core`、`data/telemetry/detail`，随后退出。升级守护在 15 秒存活检查内看到服务不活跃，恢复旧二进制并报告 `upgraded service did not remain active`。授权站同步到 4.8 只代表程序包已分发，不代表节点数据已完成迁移。

## 迁移实现

- 新增离线、copy-on-write 的存储迁移：旧库先复制到私有 staging 目录，再用与 `26.10.4.7` 完全相同的 `mace-kv 0.1.1` + `btree-store 1.0.0` 打开副本；打开副本会重放已提交 WAL，并按 4.7 运行时的语义截断崩溃留下的不完整 WAL 尾部。原目录从不以写方式打开。
- 每个 bucket 以不超过 1 MiB 的事务写入 `data/mace-v2/` 下的新库；提交后重新打开新库，逐 bucket 核对记录数与 SHA-256，并通过 Mace 完整性检查后才把整个 staging 目录原子 rename 发布。
- 发布同时写入 `migration.json` 回执（旧库树指纹、字节数 + 每个 store 的 bucket 摘要），全部成功后写 `migration.ready` 激活标记。每次启动都核对旧库指纹；首次激活前还会逐 bucket 核对新库摘要，激活后不再把迁移时的摘要当作运行期不变量。
- 回滚后旧二进制若又写入数据，先构建并验证新的 v2 树，成功后才归档上一棵为 `data/mace-v2.stale-<uuid>` 并切换；重建失败时原树保持激活。旧库被整体删除时继续使用已激活数据；只删除一部分会拒绝启动，而不是把已删除的 store 重建为空。
- 迁移前检查剩余空间（约旧库两倍加 256 MiB），失败重试会替换上一次的 staging 目录；旧目录始终保留，回滚到旧二进制仍可照常启动。
- 管理端下发的原地升级由旧二进制的 supervisor 重启服务，新二进制在 PID 锁之后、打开任何存储之前完成迁移；安装器则先停止服务，再用候选二进制预执行同一命令。两条路径共用同一实现，失败时安装器回滚二进制、旧数据不受影响。

## 测试

新增集成测试使用 `mace-kv 0.1.1` 真实写入的数据：覆盖未干净关闭但已提交的 WAL 重放、已删除 key 不复活、空 bucket 保留、迁移前后源目录逐字节不变、回滚写入后拒绝陈旧 v2 状态、损坏 manifest 拒绝激活且源文件保持原样，以及启动时自动迁移与 `.ready`/回执完整性检查。

## 兼容性与限制

- 首次启动需要迁移的节点停机时间与旧库数据量成正比，期间尚未开始监听；可快速判定的失败（空间不足、旧库损坏）会在升级守护窗口内触发自动回滚，迁移中途失败则由 systemd 重试并保留旧库与旧二进制备份供人工恢复。
- 节点任务升级的存活检查只覆盖前 15 秒；迁移超过该窗口后若中途失败，控制面可能已记录升级成功，需要人工恢复（旧库与旧二进制备份保留）。
- 每次启动都会完整哈希旧库以检测回滚写入，旧库很大时会增加启动时间；回收旧库后该项开销消失。
- 旧二进制不会自行迁移；从 4.7/4.8 升级到本版本时，迁移由 4.9 首次启动完成。
- 迁移不删除旧库，额外占用约一份旧库大小的磁盘；确认不再回滚后，可把 `data/metrics.mace` 与整个 `data/telemetry/` 一起删除来回收空间，参见 [docs/mace-migration.md](../docs/mace-migration.md)。备份/恢复节点数据时必须保留 `data/mace-v2/migration.json` 与 `migration.ready`，缺少激活标记时启动会 fail-closed。
- 组件版本按 `YY.MM.PATCH[.x]` 管理；Cargo 保持三段 `26.10.4`，本次完整产品版本和 tag 为 `26.10.4.9` / `v26.10.4.9`。

发布包、SHA256 清单和多架构 GHCR 镜像由 tag 触发的 Release workflow 构建；镜像复用已验证程序包中的同一份二进制。
