# 已存缓存响应头：直接逐字段验证候选

当前是候选实验，尚未替换生产路径，也没有可报告的性能收益。

此前 CPU 采样指出缓存准入和已存响应头校验有可见开销。Range 分支已经单独减少普通请求的预检查；
本轮针对仍必须执行的校验本身。旧实现把所有字符串还原成临时 `HeaderMap`，再检查共享缓存与响应边界。
候选对不超过 32 个字段的元数据逐项验证，省去临时 map，继续使用同版本的 `HeaderName`、`HeaderValue` 解析器。
更大的元数据走完整旧实现，保持原容量边界，不增加字段数量拒绝条件。

重复 Content-Length 必须一致；非法字段、不可无损转为文本的值、Vary、Set-Cookie、敏感缓存指令、
不可存储的逐跳及 framing 字段仍拒绝。没有减少缓存安全检查，也没有更改生产缓存格式。

Actions 将对不可变基线 `a79b20d22c32e2b77c926e2335792b874b1d8bc8` 做三万多组差分，
保留每项判定，再分别测分配和计时。八轮交替顺序、八种输入、每种二十块，共计划 2560 个计时块。
依赖版本及 checksum 与生产锁文件一致；分配计数不进入计时程序。

仍需确认语义一致、典型和拒绝路径的收益或退步，再决定是否移入生产并运行完整 CI。
组件收益不能等同节点吞吐；旧版的大容量 HeaderMap 限制也不会由该候选解决。经审批的功能降级：无。
