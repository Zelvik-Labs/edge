# Edge 第二批架构优化与独立对照（2026-11-02）

本轮在[第一批生产优化](performance-architecture-implementation-2026-11-02.md)之上继续实施，不把更早版本的收益重复计入。对照基线为上一批 `64d0dc7b…` 生产二进制；Nginx、OpenResty 和两个 Edge 版本逐一独立运行。RKE 继续暂停，使用当前共享云环境。

**结论：完成了第二批实现，测得 H1 缓存命中收益，但本轮候选未通过全面性能提升的验收，也未超过 Nginx/OpenResty。** H1、1 KiB、连接复用三轮中位数：HIT 每成功响应 CPU 从 87.56 降到 78.26 µs（−10.6%），吞吐从 18,683 到 20,728 RPS（+10.9%）；OFF 的 CPU 则增加 7.2%。扩大到 32768 唯一键的冷缓存批次，CPU 增加 13.0%，吞吐下降 9.8%。H2 复测仍有明显回退，不能用最初的一轮异常或个别有利样本代表全部结果。

这台共享云存在较高 CPU steal，多个组的吞吐极差超过中位数的 15%。例如新 Edge 的 H1 HIT 为 13,801–22,659 RPS。CPU/响应减少是本轮观测值，不是已确定的生产收益；回退也尚未通过单项消融定位到某项修改。当前版本保留在隔离工作树，未发布。

## 已实施

| --- | --- | --- |

## 比较方法

- 每个协议、缓存状态、连接模式、重复场景都重启目标和 tmpfs；任一时刻只压测一个产品，编译完全停止后才开始。
- 目标 CPU 0–1、2 CPU 配额、2 GiB；客户端 CPU 2–3；源站 CPU 4、1 CPU。父级 `cpu.max=800000 200000` 实际总配额为 **4 CPU**。CPU 编号分开不等于独占硬件，steal 与客户端/源站消耗随样本保留。
- 两个 Edge 均为 Rust 1.99.1、x86-64-v2、opt-level 3、fat LTO、codegen-units 1、panic abort。Edge 控制端处于目标 cgroup，计入 CPU；竞品无业务 Lua。访问日志、业务 WAF、自定义指标关闭；基础统计与内置保护保留。
- 原生客户端校验真实协议、TLS 证书、HTTP 200、完整正文。HIT 要求窗口内回源为零，干净 OFF/MISS 要求回源数等于成功响应数。全部失败和未知值保留。
- “场景通过”表示上述协议、正文、回源和连接契约通过，**不表示吞吐或 CPU 已达到性能目标**。性能回退单独列出。
- reuse 为 32 连接各一在途请求；H2 multiplex 为 2 连接各 16 在途；fresh 为每响应建立新连接，TLS session cache 关闭，2048 请求有界批次。没有把新连接结果混入复用结果。
- 版本与竞品交叉顺序，第二轮相邻反转。窗口前记录两秒空闲 CPU 参考，不从测量值扣除，也不声称已经完成后台稳态预热。
- CPU 为整个目标 cgroup 的 µs/成功响应；RPS 为成功响应数/客户端窗口时间。P99、错误、连接数、回源数、内存峰值、客户端与源站 CPU、steal 和文件系统占用均在逐样本 CSV/manifest 中。
- 同一 RSA 2048 位证书。第一组保留产品默认 TLS 协商；补充组通过客户端配置统一 TLS 1.3、AES-256-GCM、X25519，单独报告，未更改生产服务端安全配置。缓存为 tmpfs，不代表真实磁盘写放大与耐久性能。

测试控制端只实现启动、认证与配置所需的 RPC。已检查的 Edge 日志仍出现后台 stream/status 等 RPC 未实现的重连/上报警告、Geo 更新失败及出站 TLS `UnknownIssuer`；容器内部分 sysctl 写入也被拒绝。这些不能混为原生压测客户端的传输错误或证书校验失败，但会限制后台稳态与完整控制面验收。两代 Edge 使用同一控制端，窗口内后台成本计入 cgroup CPU；没有为了得到更好的结果关闭证书校验或隐藏这些警告。具体观察见归档的 `fixture-warnings.json`。

### TLS 默认参数差异

额外握手探针发现：在相同客户端、证书、TLS 1.3、`TLS_AES_256_GCM_SHA384` 和 RSASSA-PSS 签名下，Edge 默认选择 **X25519MLKEM768**，Nginx/OpenResty 选择 **X25519**。因此默认 TLS 新连接表不能称为密码算法等价对比。统一算法组仅约束测试客户端的 OpenSSL 配置，并在每个场景前后用 curl 验证实际协议、套件、密钥交换组和证书校验。curl 与原生客户端均使用 libcurl 8.14.1 / OpenSSL 3.5.7；原生客户端继承同一配置，未单独覆盖组或套件。

这两组在不同时间运行，不能把两组数值相减当作混合密钥交换算法的净开销。统一算法也没有消除共享 CPU、后台任务、实现差异和单轮波动。默认算法诊断中的三次 1 秒运行不进入容量表。

## 采样归因

重新对两代生产构建分别采集 H1 HIT/OFF/MISS 的用户态 CPU 栈；采样窗口 15 秒，MISS 为 32768 个唯一键。采样只附着于 Edge 进程，不包含内核和测试控制端，不能直接分解整个 cgroup 的 CPU/成功响应。采样运行及 perf 报告处理会改变时序，所有采样运行的 RPS/CPU 均不进入容量表。包含关系的栈组会重叠，不能相加或当作删除某功能后的预计收益。

H1 容量样本还显示，候选与 Nginx 的用户态 CPU 中位数分别为 HIT **54.83 / 11.88 µs**、OFF **116.76 / 15.03 µs**；内核态分别为 **23.43 / 24.79 µs**、**63.53 / 42.39 µs**。本组差距主要在用户态，请求上下文、完整过滤链、共享统计聚合和回源对象复制仍值得优先处理；不能把差距全部归给 TCP 或系统调用。用户态、内核态各自取中位数，不保证相加等于总量中位数。

## 尚未完成和下一步重点

**仍存在的问题：** H3 缓存 BYPASS、H3 新连接批量停滞、ENOSPC 与关键遥测共享存储的隔离问题尚未修复。本轮不据 H3 OFF 功能通过宣称 H3 缓存可用。

**设计限制：** 普通请求仍穿过完整请求链，回源选路仍复制 Backend 扩展，回源准入仍覆盖连接池复用。统计 worker 虽按批接收，仍逐事件更新共享聚合器；后续应验证 worker 本地合并与按配置代交接，而非仅把队列批次调大。Bloom、正文/元信息分文件和异步文件调度仍在。

后续实现优先级和验收条件如下；这些尚未算作本轮已完成的优化：

| 顺序 | 具体工作 | 解决的问题与验收 |
| --- | --- | --- |
| 1 | 对缓存、头处理、回源模板分别构建消融版本，重测长 MISS 与 H2 multiplex/fresh | 先定位回退；统一 TLS、随机交叉多轮，保留 CPU/响应、P99 和错误。没有证据的修改不作为默认提速发布 |
| 2 | Backend 扩展改为共享不可变配置，避免选路克隆深拷贝 HttpPeer 后再次克隆 | 减少 OFF/MISS 的对象准备；覆盖热更、SNI/Host、PROXY 身份与连接池隔离，确认分配次数实际下降 |
| 3 | 配置编译生成精简请求执行计划，公共上下文与可选上下文拆分 | 已关闭的内容加工、WAF/规则和详细日志不再重复探测；开启配置仍执行原有契约，按 HIT/OFF/MISS 分别验收 |
| 4 | 统计先在 worker 本地合并，再按配置代及时间窗口交接 | 减少逐事件共享表更新；重启、热更、迟到事件、耐久交接后计数必须对账，基础计量不能消失 |

本次采样中 Bloom 符号命中为零，不能据此认定它是主要瓶颈或把删除 Bloom 列为已验证收益。HTTP 基础维度仍有实际消费者，“自定义指标没有配置”也不等于“所有 HTTP 统计均可不记录”。

**明确取舍：** 本轮未整套移除协议或基础统计。上一批“小于 64 KiB 已知长度正文不做存储压缩”的空间成本继续存在；当前变更没有解决该取舍。详细统计、WAF、内容加工若要转为不同数据面，仍需明确每类配置的功能和计量契约。
