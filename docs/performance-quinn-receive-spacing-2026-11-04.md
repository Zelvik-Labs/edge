# 同一 QUIC 二进制的接收节奏控制

上游 OpenSSL 3.5.7 源码存在待验证的批次顺序窗口：QRX 先处理待收 datagram，再由通道处理帧，
本地握手确认可能落后于后续包的更新检查。此前默认组和 X25519 都出现相同 KEY_UPDATE_ERROR，混合组不是必要条件。

本轮固定原始 Edge/controller（82e3cf0）和同一个有界诊断 OpenSSL 客户端，增加 unpaced/paced/paced/unpaced 四格。
每格都是 32 KiB HIT、32 个连接槽、16,384 次 fresh 尝试，保留原期限、Retry off、GSO auto 和测试 CA/主机名验证。
两种条件都经过同一个 IPv4 loopback UDP relay，仅 server→client 发包间隔分别为 0 与至少 100 微秒；不改变密钥更新策略。
错误 CA 控制也经过对应 relay，每项必须 curl 60。实际客户端和服务端、动态库及 relay 源码哈希全部保留。

relay 在 fixture 的 origin CPU 上独占运行，不抢占指定的 proxy/client 核；该核在正式 HIT 中没有回源工作。
100 微秒控制采用最后一小段轮询，避免 epoll 毫秒取整改变实验条件。它有额外 CPU 与时序成本，整个实验不做容量排名。
流数、队列条数和字节均有限；网络错误或容量耗尽作为显式实验失败。收发计数、真实最小发送间隔、affinity、峰值队列和关停剩余均保留。
客户端退出后尚未转发的关停包单列，不能据成功响应声称所有 UDP 包零损失；也不把 relay 的发送间隔当成客户端内部逐包处理的证明。

本地真实双 UDP flow 控制已验证正文、分包边界、顺序、来源和两种间隔。正式网络对照等待 Actions。
若 unpaced relay 本身不能复现原错误，则本轮不能证明 paced 消除了故障；即使差异明显，也需继续区分网络/拥塞时序与客户端内部批次处理。
