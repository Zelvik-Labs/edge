# Edge 26.10.5 与 suite 26.10.5.1 升级说明（候选版本）

本文件描述升级要求，不表示已完成发行或生产部署。发行验证结果另附源码 SHA。

## 修复范围

- 修正 mimalloc v3 的选项访问：通过链接库自己的头文件获取具名选项，开启 page_reclaim_on_free，恢复允许 arena 分配的默认值。
- 自有 Tokio runtime 的线程使用启动、park、退出回调执行回收；Pingora 内部 runtime 尚无回调，状态继续报告 coversAllWorkers=false。
- 自定义指标按配置代、事件分钟及实际模板变量聚合；配置的日/周/月周期仅控制 ClickHouse 查询输出，Edge 不保留对应长期桶。快照携带耐久 revision 和行实例标识，完成耐久交接后立即释放行及容量 charge；同一分钟后续事件建立新实例，ClickHouse 在 FINAL 后求和，重试不重计。
- 独立 IP 改为精确 `(站点, 事件分钟, IP)` 短批次，通过 core 队列耐久上报后释放；移除 Edge 日级及实例生命周期 IP 集合，不再每请求写 UIP_*。ClickHouse 跨分钟与节点做精确集合并集。按 host 过滤的访问日志分析保留原有来源；它与全请求独立 IP 的覆盖不同。
- 内建 request_stat 按事件分钟上报，新增 server_request_stat_delta 按节点、批次、分钟及完整维度保存增量；查询先 FINAL 再求和，防止旧日级替换键覆盖不同分钟。旧表幸存行一次性复制，原时间和粗粒度保持原样。
- 遥测按稳定错误码区分可重试与确证无效；永久拒绝批次的原始压缩 envelope 和审计一起耐久隔离，收到 gap 收据后仍保留原文。
- 访问日志补充 ASN、国家代码、设备类别及独立于指标的分析生命周期；API 返回已有运营商属性和当前集群，控制台节点筛选由服务端执行。无法识别的 UA 保持 Unknown。

## 指标契约切换

旧批次不能无条件改写成新快照：旧 API 可能已提交但确认未落盘，改用新 hash 重发会与历史复制重计；旧 keepKeys 还可能依赖接收端状态。离线转换必须核对原始批次的接收结果，不能猜测窗口、键或累计值。

当前只自动执行 ClickHouse 建表和一次性历史复制（含 marker 校验）；下列切换顺序尚无自动协调实现。API 不会自动排空旧 Edge spool 或暂停其它旧 API，节点升级任务也不会校验这次指标契约的前置状态。普通滚动升级不能代替该顺序。本节是当前实现的部署限制，不是已经完成的自动升级功能。

本轮没有运行时兼容窗口。最低配套候选版本为 suite API 26.10.5.1 和 Edge 26.10.5；已发行的 API 26.10.5 不包含新的 unique_ip 与 request_stat 分钟契约。最终版本以发行记录和发布日 CalVer 为准。UploadMetricStatsRequest 的 revision（9）、windowStart（10）、windowEnd（11）继续使用；UploadServerHTTPRequestStatRequest 新增 windowStart（8），unique_ip 使用 UniqueIpObservations。事件区间为 epoch 秒的 [start,end)，新发送端不使用 keepKeys。

1. 在旧 API 仍运行时，先从外部停止新增业务并完成在途请求，保留旧指标配置及上报器运行，再排空所有旧 Edge 的内存聚合、待发和耐久 metric_stat、request_stat 批次。旧版状态中的 spool 为零不能证明内存已空；固定等待 60/120 秒也不是排空屏障。不能通过清空或禁用 metric_items 达到排空：旧版可能跳过 flush 或丢掉已移出的样本。无法确认完整排空时停止生产切换。已有历史拒绝批次不能假确认、删除或忽略，须保留完整原文并单独解决。
2. 排空后停止旧 Edge 并防止自动重启，再停止所有旧 API 指标接收写入，确认无在途旧写入后启动新 API。停止旧进程或由数据库权限阻止旧凭据写入，才能形成实际写入隔离；新控制面内的状态标记无法约束旧进程。不能让新旧 API 同时接收指标：新 API 首次创建 metric_stat_snapshot，并一次性从 metric_stat FINAL 复制仍存活的历史行；迁移 marker 记录版本及 SQL 校验和。server_request_stat_delta 也只在首次启动从 server_request_stat FINAL 复制幸存行，并记录不可变 seed 校验和；历史分钟身份无法恢复，不作猜测。首次复制之后才写入任一旧表的行不会自动再次迁移。
3. 确认两张指标表迁移及新 API 健康后，将 Edge 升至 26.10.5，再恢复指标采集。Edge 不得先升级：旧 API 不理解累计 revision，可能按接收时间让迟到旧快照覆盖新值。
4. 核对同窗口的累计值、两个节点求和、待发队列和新表结果。控制台可与 API 独立升级至 26.10.5。

若原始 envelope 已有匹配 node_id/batch_id/payload_hash 的耐久收据，新 API 会先返回原收据以补确认，不转换数据。没有匹配收据时，新 API 遇到 metric_stat revision=0 返回 telemetry.metric_snapshot_version_required；request_stat 缺少 windowStart 返回 telemetry.request_stat_window_required，均为 retryable=true。原始批次继续留在 spool；它不会被当作累计快照，也不会被确认或丢弃。现有 spool 按 core/detail 两条 lane 排序，残留旧批次可能占用 detail 队头并影响后续批次的连续回收。此行为不等于自动转换旧数据。

## 历史与回滚

旧 metric_stat 表不删除、不重写。迁移只复制旧表 FINAL 仍保留的行；旧 ReplacingMergeTree 已覆盖掉的节点或增量贡献无法恢复。历史行保留 event_time，无法可靠推导的 window_start 为 0；查询从新表读取迁移历史和新快照，使用 FINAL 后按系列求和。

切换开始后应前滚修复。不能直接恢复旧 API/旧 Edge 并继续同周期指标写入：旧表不会接收新快照的迁移结果，重置或删除 Edge checkpoint 还会生成新 epoch，使当前累计值再次计入。回退前必须暂停采集，保留新表、原始 spool、checkpoint 和隔离原文，并单独确定数据转换方案。

## 验证和容量边界

THP 保持开启，遵循宿主与 mimalloc 的分配策略；进程级关闭 THP 仅是历史归因对照，不是产品修复。RSS 包含大页和已释放但驻留的内存，需结合存活对象与回收证据判断，不能只凭某个瞬时 RSS 定性泄漏。

短时回归仅验证本次输入、进程和观察窗口，不能证明长期无泄漏。生产部署不属于本次发行动作。

隔离原文计入磁盘预算，未实现自动删除或离线转换工具。归档达到预算时会明确背压，不能以无限磁盘保证无限保留。checkpoint 无法读取或写入时保留原文件并报告错误，不通过重置 epoch 伪造恢复。

内建 request_stat 以完成事件分钟确定时间，不再使用 flush 时的日期。独立 IP 以请求开始时的分钟确定身份；ClickHouse 对任意查询周期执行 uniqExact，不相加各分钟的独立数量。旧带宽标量 countIPs 不再作为独立 IP 来源。旧 UIP_* 和本地历史计数槽原样留存，不重载到内存、不继续写入；新身份表无法补回切换前未上报的逐 IP 身份，历史日/月粗桶也不能恢复逐分钟分布。

日志的集群表示节点当前的有效成员关系。系统没有可返回的分组模型时，分组保持缺失；不会构造默认分组或猜测浏览器、系统、ASN。
