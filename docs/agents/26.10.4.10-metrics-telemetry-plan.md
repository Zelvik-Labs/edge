## 2. 指标根因（行号对应本方案基线）

### M1：无消费者仍采集、空配置没有生命周期出口

- `src/metrics.rs:1889` 对所有事件无条件调用 `METRIC_STAT_AGGREGATOR.record`，没有检查启用项或 category。
- `src/rpc/stats.rs:1753-1758` 在 `metric_items.is_empty()` 时返回 None，不 flush。issue34 明确保留了旧行为，因此合并不修此缺陷。
- 复现：不配置指标，持续发送 HTTP 请求，即可在没有上报消费者的情况下增长到字节预算；以后新维度持续拒绝。只配置 HTTP 指标时，TCP/UDP 的无消费者样本也会先进入同一聚合器。
- 既不能一直保留这些无消费者记录，也不能在重新启用时把旧请求按新配置/新时段归属。

### M2：保存完整请求上下文，近似逐请求留存

- `src/proxy.rs:9453` 每请求构造 `metric_request_context`。
- `src/proxy.rs:1887-2110` 等代码构造约 74 个静态属性，加动态请求头、Cookie、query、响应头；包括唯一 requestId、时间、完整 URI、headers 文本及其别名。
- `src/metrics.rs:1885` 再 clone 整个 values BTreeMap。
- `src/metrics/aggregator.rs:140,331-354,514` 自定义指标保存完整 attrs 作为嵌套 BTreeMap 的 key；只要 requestId 不同，即使最终仅按 country 分组，两条请求也不能合并。
- 内建 HTTP 统计 `metrics.rs:1898` 也携带同一个包含 attrs 的 AggregationKey，实际消费者 `rpc/stats.rs:1946-1987` 仅需要地域、运营商、系统、浏览器、WAF 维度。
- 当前预算 `memory_governor.rs:4897` 有 16MiB 下限，且 `MetricAggregator.used_bytes` 是每个实例各自计费，两个实例并非共享一个 16MiB 总池。聚合、队列、上报临时表、pending 和 allocator 的容量均须分别解释。
- 按现有估算器每属性128B allowance计算，74字段仅该项就约9.25KiB/样本，还未加字符串容量及结构；16MiB很容易在数千条甚至更少请求后触顶。这是计费量级说明，不是生产活对象数量或实际heap测量。

### M3：触顶后总数和维度明细分离

- `aggregator.rs:341` 先累加 entry 总数；新 request sample 无法 charge 时跳过样本（351）。
- `rpc/stats.rs:1236-1246` 只要 request_samples 非空就只遍历样本，不补 entry 总数的差额。
- 复现：同一个主维度，第一条 attrs 入表，第二条不同 requestId 在预算边界被拒；entry.count=2，上传维度 count=1。
- 已有 `byte_budget_rejects_key_and_sample_before_allocation`（aggregator.rs:790）实际上断言了这个分离状态，未验证最终上传总数。
- 要求：不能把现有样本丢弃包装成“背压无损”；预算拒绝必须明确计算到 droppedSamples / droppedRequests，并保证已接纳数据的总数与维度一致。

### M4：flush 不等于内存释放，预算提前退款

- `aggregator.rs:400-410` clone 全量 key、逐条 remove 并立即 refund，样本仍在返回 Vec 中；同时新窗口可继续消耗完整预算。
- DashMap remove 不主动缩容，历史峰值的桶容量仍保留；逻辑计费为零不能证明内存回到基线。
- HTTP request_stat 还有远程连接门槛 `rpc/stats.rs:1879-1884`：连不上 API 时在本地 flush 前 continue，本地耐久 spool 因而失去离线缓冲作用。
- 决策：窗口交接转移所有权与计费，旧窗口到完成持久化/丢弃策略真正执行时再释放；旧表退役后释放其容量。

### M5：issue34 pending 有磁盘副本，但仍常驻完整 protobuf

- `rpc/metric_stat_cache.rs:321-325` PendingMetricUpload 持有完整 request；`persist_pending:690` 写盘后未释放它。
- `pending_bytes:648` 只计 encoded_len，不等于 String/Vec/结构的实际 heap；默认 64MiB 是后续 flush 的背压阈值，不是物理 RAM 硬上限。
- `recover_pending:426-457,730-750` 把所有 pending 文件读入/解码为集合，再全部装入队列；具体复现输入是大 pending 目录重启，恢复阶段绕过流式字节上限。
- `dispatch_metric_uploads:1613` 一份样本可能展开为多个指标项；单次展开不保证小于一次 aggregator 的预算。现有“本 tick 有界”注释不能取代展开字节计费。

## 3. 推荐实现：单一生命周期，不靠扩容掩盖

### P1：按配置编译采集计划

在配置发布路径编译不可变 MetricCollectionPlan，包含启用 item、category、item/version、窗口规则和模板。与 ConfigStore 的配置代一致地发布；事件持有生成时的计划，禁止排队事件在重载后套用新配置。

- 没有启用的自定义指标：不构造、不 clone、不入队自定义 attrs；内建 HTTP/带宽/日报/IP统计照常。
- 只计算模板实际引用的维度；推荐直接按 `(item_id, version, event_window, server_id, resolved_keys)` 聚合 count/bytes/attack，无需保存完整请求样本。用户明确配置 requestId 作为维度时仍保留其语义，不能擅自合并或截断。
- 内建 request_stat 使用专用轻量 key，不携带请求 attrs，也不按不需要的维度做全量笛卡尔组合。
- 删除/停用配置：停止新采集；已接纳的旧代窗口按旧身份持久化后退役。对当前误采的无消费者数据不补造新指标；需要释放时保留原始本地归档及原因，不能以无消费者为由静默销毁已接纳数据。
- 对原字节上限不做一刀切调低；先去掉无效留存，再用测得的结构/载荷成本分配总池。

### P2：窗口、队列与上传交接持续计费

- 原子切换活动窗口；使用一个短临界区把 map、计数和字节所有权一起交给 uploader，不在遍历期间阻塞请求。
- 队列中的投影事件、活动窗口、待持久化窗口、序列化中的单批都有字节计费；预算从一阶段转移到下一阶段，禁止 flush 后先归零再额外持有对象。
- 队列同时有条数/字节限额；批次逐块构造、持久化、释放，避免 grouped/by_server/requests 全量展开与 clone 同时常驻。
- 已落盘 pending 以内存索引/路径为主，按有界页/批次读取和重试；恢复目录按顺序增量加载，不一次解码全部。
- 磁盘满或持久化失败保持明确错误和背压；不得增加“静默丢弃、假成功、假 ack”。现有满载拒绝必须保留并准确上报，不承诺有限资源下无限期无损。
- 多个 item 的编码量计入真实总池；保留已接纳样本语义，不因一个 item 的展开挤掉另一个 item。

### P3：保持 issue34 allocator 修复，但不夸大覆盖

保留 C 头具名选项桥、版本/回读断言、page_reclaim_on_free=1、disallow_arena_alloc=0，以及 Tokio 生命周期回收。Pingora 尚未挂接的 worker 继续报告 coversAllWorkers=false；不修改 vendored Pingora，不将其冒充全线程回收。

本轮不改宿主 THP、不通过生产重启掩盖增长，也不把 16MiB 逻辑 charge 当作可保证的 RSS。

### P4：可核对的观测口径

保留总览 gauge，同时按组件报告，避免一个 `metricsAggregatorBytes` 混合多种所有权：

- 自定义指标：enabledItems、activeGeneration、activeWindows、entries、计费字节、待交接窗口字节、最近flush时间、拒绝请求/维度数。
- 内建HTTP统计：entries、计费字节、上次本地持久化时间；和自定义指标分开。
- 维度队列：queueEntries/queueBytes，按条数或字节拒绝的数量。
- pending：内存已加载字节、磁盘待发字节、最旧时间、恢复扫描进度；不能以protobuf长度冒充heap。
- 遥测：每lane的head/tail、pendingBytes、oldestAge、ackedAhead、失败类型、隔离数量/字节、最近成功时间；同一坏批次日志去重后周期汇总，不能静默隐藏。
- allocator：版本和关键选项、committed/reserved、可安全获得的abandoned信息；不增加在线gdb注入作为日常采样依赖。

## 4. 遥测与指标统计接收契约

控制面基线 `f1f019653b87c9c9c7ee7c238e131ec883a4e419`，以下文件在调查时无未提交修改。

### T1：历史归属拒绝没有稳定码，形成永久毒头

- `control-plane/internal/gcloud/telemetry.go:112-136` 按事件时间查询部署区间，不匹配返回裸 PermissionDenied；assignment/route 不匹配同样见92-109。
- 部署历史 `internal/infra/postgres/telemetry.go:398-433` 的 valid_from 使用配置生成时的 time.Now；重新下发配置不会自动补齐过去的部署证据。因此10月22日的旧时间点不会仅靠重试而变合法。
- Edge `telemetry.rs:1862-1916` 对裸 PermissionDenied 保留Retryable。这对可恢复凭证是正确的，但历史归属拒绝缺少区分。
- `telemetry.rs:687-694` 对后续成功批次记录ack但保留payload；`collapse_confirmed:719-725` 遇到未确认head即停止。因此后续可继续成功上传，retainedBytes仍不能释放，直到容量耗尽。
- 推荐：在既有zelvik-error / zelvik-retryable trailer上定义deployment_missing、assignment_invalid、route_invalid的精确语义，写入errors.md；裸PermissionDenied与可恢复credential/instance错误仍重试。仅有“当前查不到历史”时，先确认是否缺历史证据，不能将其当成“曾经非法”的证明。确证无法归属的历史原批次转持久隔离，记录原因，不再每轮重试。
- 重要：现有 `quarantine_head:779-864` 实际删除原payload，只保存LossRecord+gap（798/814），不是完整原文归档。4.10必须扩展为原批次与原因的耐久隔离，成功落盘才推进head；不能直接套用现有删除路径并称之为无损。

### T2：窗口内新部署被点查询误拒绝；混合批次扩大拒绝面

- bandwidth解码 `internal/infra/clickhouse/batches.go:119-128` 用窗口/segment起点做At，却未设置Until，进入部署点查询。
- 可复现：12:02部署，首批的窗口起点12:00；查12:00尚未部署，整批被拒，即使请求确实发生在12:02以后。
- 改为真实统计segment的[start,end)与部署/assignment/route交集授权；保持统计窗口键与事件归属，不通过改写窗口键绕过授权。复用现有TelemetryAggregateAnchor查询思想（postgres/telemetry.go:366-375），但授权锚点与最终存储键分开。
- 只要一行不合法，API当前拒绝整批（gcloud/telemetry.go:132），一个server会阻断其它合法server。推荐Edge在同一kind/window内按server分批，API仍全批验证后耐久确认；旧混合批次保留原文供恢复/审核。不要实施“跳过坏行然后返回整批成功”，那会改变receipt含义且掩盖损失。
- 时钟偏快单独处理：UploadBatch:29将未来>1min与坏格式合并为InvalidArgument；Edge视为永久错误。拆成既有control.clock_skew可恢复状态，时钟恢复后仍可发送原批次。

### T3：pending不等于retained，遥测内存与磁盘分开治理

- telemetry.rs:1018的pendingBytes扣除了ackedAheadBytes；真正占lane容量的是retainedBytes。必须同时显示pending、retained、ackedAhead、oldestAge及head错误，避免小pending掩盖大保留。
- Mace的WAL/cache/pool/checkpoint是每lane的内存工作集，不是队列磁盘大小。不能把磁盘排空等同于RSS同比下降。
- 修复坏head后验收collapse推进与retained下降；不手工删库/队列，不伪造receipt。持久隔离也纳入磁盘预算；满时显式背压，保留原文件并告警。

### S1：指标接收端是快照覆盖，Edge发delta导致少计

- `internal/infra/clickhouse/batches.go:148-155` 原样写value，没有累计或处理keep_keys。
- `schema.go:80-96` 为ReplacingMergeTree(ingested_at)，排序键(server_id,item_id,time,hash)。
- Edge每60s flush一次增量，但时间键可为5分钟/小时/天；同周期先发10再发50会覆盖为50，正确累计应60。
- issue34恢复的去重在本地spool成功后commit（rpc/stats.rs:1649），但远端可能拒绝原批次；下次只发keep_keys，远端实际没有这个值。4.9已经移除过该优化，不能合并后原样发布。
- 推荐：按事件时间维护周期累计快照、持久checkpoint后逐批发送；删除未确认值去重/keep_keys优化（不删除必需的pending持久化能力）。失败重试发送同一快照，重启恢复累计基线，禁止重启后从0覆盖已有周期。

### S2：快照主键与乱序版本也必须修，不能声称只改Edge就够

- 当前metric_stat有node_id列但ORDER BY不含它，Edge的hash同样不含node。两个节点对同站点/指标/周期/维度发送值10和20，将互相替换而非保留节点贡献。该缺陷能由两节点同维度输入直接复现。
- 接收端用ingested_at作为覆盖版本；遥测并发和历史重试可能让旧快照晚到，覆盖新快照。只改为累计发送仍不正确。
- 4.10快照身份必须包含node、item/version、window、维度；使用产生端单调snapshot revision决定新旧，并使重试同一快照幂等。节点重启的revision/累计checkpoint一起耐久化；不能仅用每次随机boot的sequence比较。
- 这涉及ClickHouse真实迁移与读查询调整，不能仅改schema.go新装基线。具体迁移先给出新表/切换、历史保留与回滚影响，再执行；不得默认重写/删除旧数据或加双读兼容层。当前已被旧ReplacingMergeTree合并丢失的节点贡献不能凭空恢复。
- 不必修改protobuf即可利用既有batch身份/载荷版本信息，但具体revision载体必须在Edge/API契约测试中定死，不能假设ingested_at具有源端顺序。

### L2：确定缺陷与修复契约
