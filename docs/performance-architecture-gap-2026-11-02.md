# Edge 与 Nginx / OpenResty 的架构差距和改造顺序

日期：2026-11-02，Asia/Hong_Kong。基于 `01a2156882789f876f3c40c01bc6a0ee0bc5fa2b` 上已测的工作区代码，生产二进制 SHA-256 为 `94e8026636a67c69c6abb2f70f5c5259ee54a1eee44353640f547a55a068f645`。

**结论：普通请求仍经过较重的通用链路，回源又增加了 Header / Peer 构造和通用流转发成本，冷缓存再叠加自动压缩、文件任务切换和元数据发布。这些是具体的实现与架构成本。还有 H2 轮换、H3 缓存准入方面的问题，但它们不能解释 H1 的全部差距。现有证据不支持把原因归结为 Rust 天生慢，也不足以断言必须替换 Pingora。**

若性能优先，应把普通缓存命中与普通反代做成紧凑的数据面，让配置决定实际执行哪些步骤；将昂贵的内容加工和详细分析移出基础路径。仅删除一个统计模块或关掉 WAF，达不到当前所需的改善幅度。

此次建立了热点与代码结构的对应关系，尚未逐项完成消融实验，不能把全部差距精确分摊给每个模块；下面的删除与重构建议也不能视为已经测得的提速。

本轮完成 4 份当前生产构建的 CPU 采样，合计 **10,143 个用户态样本，丢样为 0**；对应 387,337 个成功且正文校验通过的请求。另独立完成三产品、三状态共 9 次系统调用诊断，107,974 个请求全部通过。**本轮没有修改生产 Rust 代码、删除功能或发布版本；这是改造依据，不是已经超过竞品的结果。**

**差距首先发生在哪里**

下表来自上一轮正式矩阵：1 KiB、H1、32 个复用连接、代理 2 核。单位为每个成功请求消耗的 CPU 微秒，三次独立样本的中位数。用户态、内核态分别取中位数，因此两列之和不一定等于总 CPU 的中位数。

| 状态 | Edge 总 / 用户 / 内核 | Nginx 总 / 用户 / 内核 | OpenResty 总 / 用户 / 内核 |
| --- | ---: | ---: | ---: |
| 缓存命中 | 90.33 / 62.18 / 28.87 | 41.68 / 13.28 / 28.69 | 34.38 / 11.01 / 23.37 |
| 无缓存回源 | 213.24 / 136.39 / 76.85 | 63.01 / 16.55 / 46.47 | 52.02 / 14.13 / 37.52 |
| 冷缓存写入 | 1001.70 / 469.25 / 532.45 | 318.43 / 46.41 / 274.36 | 410.91 / 73.17 / 342.55 |

命中时 Edge 与 Nginx 的内核成本接近，用户态却约差 4.7 倍；回源的用户态成本约差 8.2 倍。优化重点应先放在应用数据面。AF_XDP、更多连接、更大的内存预算，都不能直接消除这些用户态工作。

此前已通过源站 TCP 计数确认三者大量复用回源连接，所以“Edge 每个请求都新建 TCP”不成立。自定义指标、访问日志、业务 WAF 规则和 XDP 均未在此基准中开启；基础计数、内置统计、内存与连接保护仍开启。OpenResty 没有执行业务 Lua，本轮主要比较的是它的 Nginx 核心路径；其更高吞吐不能解释成 Lua 更快。

这些 CPU 数值比单独看 QPS 更有诊断价值，但仍是共享云机器上的探索性结果：正式窗口的最大核心 steal 中位数约 40%，客户端也可能受限，代理 CPU 包含 Edge 的测试控制器。不能据此声称稳定的生产性能倍数。完整条件见[正式协议／缓存／连接矩阵](performance-protocol-state-comparison-2026-11-02.md)。

以上是 **用户态调用栈的包含式分类**，按符号匹配；内联会影响归类，类别存在交叉，不能相加，也不能把某个父调用栈的全部时间认作该函数自身成本。回源的 `proxy_to_upstream` 包含约 50.7% 的样本，其中也包含 Edge 回调、Header 和内存分配，不能称为“Pingora 自身占 50.7%”。零样本不代表零成本。

CPU 采样在包含 perf 工具的诊断镜像中装载同一生产二进制，代理 CPU 配额仍为 2 核；perf 本身也消耗该配额。采样只附着生产 Edge 进程及其线程，工具进程不计入上述调用栈。它用于定位当前工作构成，不是无扰动的前后性能实验。

第一份冷缓存采样为 744 样本，Zstd 18.95%、创建 context 7.12%；独立扩大到 32,768 次冷缓存请求后，上述比例仍分别为 17.28%、6.31%。后者客户端约 19.4 秒，采样 20 秒，减少了短负载结束后后台任务占比偏高的影响。两份都严格验证每次回源和正文。

这说明默认逐对象压缩是实在的优化对象，但删除它不能带来三倍提升：它只是冷缓存**用户态**工作的一部分，命中场景甚至不走压缩。基础统计也有成本，但仅消除后台消费者无法填平当前差距。`memory_governor` 和未配置业务规则的 WAF 都没有显示出足够大的占比，不能将其列为主因。

**系统调用改变了一个重要判断**

| 状态 | Edge 次数 / 成功请求 | Nginx | OpenResty | Edge futex / 成功请求 |
| --- | ---: | ---: | ---: | ---: |
| 命中 | 4.65 | 7.12 | 7.09 | 0.86 |
| 回源 | 7.75 | 5.34 | 5.21 | 1.26 |
| 冷缓存 | 36.50 | 30.10 | 30.19 | 16.17 |

Nginx / OpenResty 的命中路径每次仍有文件打开、发送和关闭，而 Edge 能从 L1 返回。所以“Edge 因为命中时做更多文件 syscall 而慢”不符合此次证据；这也是紧凑内存命中路径争取超过对手的机会。

冷缓存时，Edge 的 Tokio 文件操作与元数据确认需要多次交接，futex 明显增多。应评估把创建目录、写入、发布等连续工作组织为有界执行单元，减少 executor 往返，而不是只减少几次文件调用。**futex 可能用于等待、唤醒或正常同步；此次计数不能区分锁竞争来源。strace 的累计等待时长不能当成 CPU 占比。**回源还观测到约一次 `getpeername` / 请求，其实际触发位置需进一步采栈，不能据此说 SocketDigest 没有缓存——源码已有 `OnceCell`。

这九次是 ptrace 诊断，负载和时序被显著扰动；只用于解释调用构成。采样／trace 包装器还包含启动或报告生成耗时，manifest 中这些运行的 RPS、elapsed、CPU/200 **全部排除在容量比较之外**。Nginx 冷缓存的目录创建、rename 重试也在计数内，不能假定不同 syscall 单价相同。

本轮缓存与遥测数据放在 tmpfs；确认流程可以观察，但不能用它验证真实介质的持久性、断电恢复或物理磁盘冷读性能。

**协议问题必须单独修，避免把状态差异误算成架构输赢**

H2 的 `H2_CHURN_STREAM_LIMIT=200` 累计正常接受的流。正式矩阵中的 Edge H2 有错误，但让 Nginx 同样每 200 请求轮换后，当前客户端在 multiplex 下也出现同类 CURL56。已确认轮换策略影响结果，仍需验证客户端兼容性和服务端关闭顺序；不能将所有错误单独归罪 Edge。

H3 的缓存当前明确被 `ProtocolBodyNotProvenEmpty` 拒绝，HIT / MISS 请求实际上 BYPASS。应由原生 H3 session 向准入层提供可靠的请求体结束信息，再让真正无请求体的请求使用缓存。直接删安全判断会引入缓存语义风险。H3 新连接批量超时也仍需独立排查清理、准入和客户端交互；目前没有证明内存耗尽或某个固定连接数硬上限。

冷缓存还暴露过小容量测试盘 ENOSPC 导致遥测 Mace 的 fail-stop。这是独立的资源隔离／稳定性问题：缓存填充与关键遥测存储应有配额或保留空间，不应通过吞掉持久写错误来修。正式矩阵已重新逐案例清空 tmpfs 并排除此类污染。

**下一阶段实施顺序与超过的标准**

1. **先取得同构最小 Pingora 基线。**同一代码版本、构建、allocator、证书、客户端及网络，测纯转发与完整 Edge 的 CPU/请求差值。探针明确缺少业务功能，只用于定位，不能当作生产 Edge 成绩。用它决定通用引擎与 Edge 附加链路分别需要改多少。
2. **重构普通请求路径。**在已有编译计划上增加执行能力与依赖，普通 H1/H2 缓存命中／反代使用紧凑上下文；功能状态延迟建立；提前编译 Header、origin 不变参数，移除上述重复准备。缓存安全和已启用规则的执行顺序保持一致。大部分命中用户态工作都分布在这条路径，优先级高于继续局部模板微优化。
3. **改缓存填充。**先独立对照“小对象原样存储”和“复用压缩上下文”，再合并文件操作、减少跨执行器交接，最后评估正文与元信息同文件的格式。现有 Mace writer 已会把队列中已有命令合并事务，不能把“增加批量提交”当成未实现的新发现；应测实际批大小、确认延迟和数据库之外的开销。所有路径保留发布失败、purge、重启恢复和墓碑测试。
4. **把详细分析和内容加工从基础数据面拆开。**按实际产品取舍移除或外置；仍需要的精确统计按 worker 聚合，按消费者需求提取。没有配置自定义指标时不应再准备其上下文；基础业务统计是否保留与自定义指标是否存在是两个独立开关／契约。
5. **并入 H2 / H3 修复后做协议回归。**H2 正常复用不产生低阈值错误轮换；H3 必须有真实 HIT、真实 MISS、无缓存及新连接的可比结果。若最小引擎基线仍不满足 CPU 预算，再考虑在自有 crate 实现专用普通反代引擎；保持 vendored Pingora 只读。直接换语言或换框架不算已经证明的优化。

以当前每个状态中 CPU 成本最低的竞品为参照，若希望在 CPU 约束下争取 **10% 吞吐优势**，可把下面作为初步工程预算：

| 1 KiB H1 / 复用 | 当前 Edge CPU µs/请求 | 初步目标 CPU µs/请求 | 需降低 |
| --- | ---: | ---: | ---: |
| 命中 | 90.33 | ≤31.26 | 约 65% |
| 回源 | 213.24 | ≤47.29 | 约 78% |
| 冷缓存 | 1001.70 | ≤289.49 | 约 71% |

预算按“竞品最小 CPU 成本 ÷ 1.1”计算，是同等工作、CPU 约束假设下的方向性门槛，不是对实际 QPS 的保证，也不是本轮已经实现的结果。必须在低 steal、客户端与源站有余量的机器重建稳定基线。

验收应逐项对照相同协议、证书、响应内容、缓存状态和复用策略：先完成三个主路径的独立重复实验，再扩展 1 KiB / 32 KiB / 大对象、TLS、H2 / H3、多路、关闭连接和慢客户端。报告同时给出吞吐、P99、错误率、CPU/请求、RSS 与存储写量，精简配置与完整配置分列；长期稳定性按 1 小时、24 小时、72 小时推进。此次没有完成这些长期测试，也没有宣布任何全面超越。
