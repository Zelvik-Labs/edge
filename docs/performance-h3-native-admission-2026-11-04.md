# 原生 quiche 新连接限制的定位（2026-11-04，香港时间）

最终诊断确认：2 GiB 容器内 tokio-quiche 大量新连接失败，首先触发的是 Edge 自己的
**request workspace 子预算**，不是共享账户余额耗尽，也不是已修复的 FIN 问题。
`74f5325` 的最大可能队列预留占用了错误的子预算。`dabf21e` 已将其移至全局容量账户，
保留最坏容量扣减及释放确认。后续 `183c583` 探针又确认短连接周转会积累未确认释放额度，
`b30f0cf` 增加额度不足时的物理观测与一次重试，2 GiB 正式探针及同机对照已通过；
持续 262,144 次连接检查随后暴露更早的连接准入入口仍会受同一释放窗口影响。
`562d49c` 已将确认移至原生容量存在时的公共字节门槛，功能 CI 通过 1350+16 个测试，
连接矩阵和持续周转正在独立 CI 重新验收；默认仍为 Quinn。

## 直接证据

[三轮探针 41677183342](https://github.com/Zelvik-Labs/edge/actions/runs/41677183342)
使用 `74f53256ba85ad0ed3bae8424db7d21a037c10c2` 的真实生产构建：
H3/HIT/fresh、1 KiB、32 并发、每轮 512 请求、每轮新进程。
包含最终 Linux 接收上限、5 MiB/连接预算及固定上游 FIN 修复。

| 轮次 | 成功 | 失败 | 首次拒绝时 workspace 用量 | 共享账户仍可授予 |
|---|---:|---:|---:|---:|
| 0 | 62 | 450 | 498,073,600 B | 1,682,119,680 B |
| 1 | 57 | 455 | 498,073,600 B | 1,689,546,752 B |
| 2 | 61 | 451 | 498,073,600 B | 1,688,981,504 B |

三轮首个拒绝均为 `class="quiche_transport_bytes"`，workspace 用量为 **475 MiB**，
共享账户 `rejects_total=0`。客户端错误是建立连接前的 `curl_7/http_0/v_0`。
工作流正确返回失败，不能拿部分成功请求计算一个可比较的吞吐成绩。

代码中的因果链：

1. `request_workspace_budget_bytes` 在正常压力下约为可用内存的四分之一，此处约 480 MiB。
2. 原生后端对每个 socket 的 32 个初始连接 backlog 加一个拒绝处理槽预留 `33 × 5 MiB`。
   测试节点开启 IPv4/IPv6 两个 socket，启动即占 **330 MiB** 的逻辑额度。
3. 额外 29 个连接额度需要 145 MiB，合计 475 MiB；再申请 5 MiB 就越过当前子预算。
   连接额度覆盖握手、运行和相关缓冲区生命周期，不等于此刻只有 29 个已建立的 HTTP 请求。
4. 准入按设计拒绝，返回 TLS/QUIC 关闭；共享账户尚有约 1.57 GiB 也不能绕过 workspace 上限。

先前曾怀疑共享账户“已归还但等待物理观测确认”的累计承诺节流。
这次直接快照排除了它作为**首次拒绝**的原因；不能把那个假设写成最终根因。

## 第二层限制：释放确认的时间窗口

将长期容量移出 workspace 后，
[183c583 三轮探针 41682837668](https://github.com/Zelvik-Labs/edge/actions/runs/41682837668)
仍有 369/1536 次失败。此时首次拒绝的 `workspace_used` 已全部为零，
共享账户 `rejects_total=1`，证据与上一阶段不同：

| 轮次 | 成功 / 失败 | 存活/待用容量 pending MiB | 已退役、待确认 MiB | 账户可授予 MiB |
|---|---:|---:|---:|---:|
| 0 | 312 / 200 | 835 | 846.55 | 65.21 |
| 1 | 431 / 81 | 860 | 832.84 | 64.57 |
| 2 | 424 / 88 | 895 | 792.77 | 66.47 |

可授予数还需要保留控制面及已建立流量额度，所以不能把最后约 65 MiB 全部用于新连接。
本轮确认的是另一层问题：高频新建/关闭在后台物理观测间隔内累计了大量已退役的最坏队列承诺，
并不是之前 workspace 根因的替代解释。代码没有依据较低的实测 RSS 擅自归还存活队列容量。

`b30f0cf` 在容量申请失败且有足够未确认额度时，强制读取新的物理内存观测，再按原硬限额尝试一次。
存活队列的 pending 预留保持原数，只有经过真实观测的已承诺额度才解除重复扣减。
没有可确认额度的满池直接拒绝，避免做无助于释放该额度的同步观测。
该慢路径的观测成本保留在完整节点 CPU 测量中；未缩短连接关闭等待或增大内存。

## 持续周转暴露的准入顺序

同版本的[完整 243 格矩阵](performance-h3-native-capacity-matrix-2026-11-04.md)中，
tokio-quiche 的 81/81 个短场景均通过；原生 Quinn 有一个独立 curl 56 错误。
这与下述持续失败并不矛盾：每格重启的短测不能证明一个进程持续接收连接时稳定。

短探针通过后，用实际 `b30f0cf` 二进制继续做一次 262,144 请求、32 并发、2 GiB 的 H3/HIT/fresh。
本地两个代理 CPU 上耗时 774.10 秒，260,579 次成功、1565 次失败：
120 次 curl 95（stream reset）、654 次 curl 7（连接关闭）、791 次 curl 28（超时）。
HIT 零回源仍成立，没有 OOM 事件。此次结果判为失败，不能以之前 1536/1536 覆盖它。

首次直接诊断为 `class="quiche_connection"`，workspace 为零，pending 为 800 MiB、
待确认承诺为 907,001,856 B，账户可授予为 65,077,248 B。
连接准入先于 transport reservation 执行，因而有可能在此前设置物理确认的位置之前拒绝。
这证明需要在公共字节门槛统一处理释放确认；不能将所有 stream reset 和超时都据此合并归因。

本机最长窗口的 host steal 最高约 **43.03%**，存在严重 CPU 调度干扰，因此不发布容量排名。
68 次进程 RSS 采样为 174.24～202.08 MiB，最后一条为 195.14 MiB；这不是泄漏排除证明。
所有 FD 读取均被宿主 `/proc` 权限拒绝，保留缺失原因，不声称完成 FD 稳定性验证。
NTP 外网校时及最小控制器未实现的后台 RPC 错误也保留，不能把这套 fixture 当作完整生产控制面长测。

`562d49c` 用生命周期计数追踪原生 transport reservation。只有启用该特性且仍有原生容量所有者时，
公共共享账户字节门槛才在失败后确认物理释放并重试一次，覆盖连接、请求和工作区。
分类型/监听器限额仍在各自原位置检查；存活 pending、控制面和已建立流量保留额度不变。
恢复成功不会增加最终分类型拒绝数；共享账户失败尝试计数仍可观察到压力。
后台确认已被另一线程完成时也重查一次硬门槛，避免沿用过时的失败结果。

## 对架构选择的影响

tokio-quiche 0.20.0 的每连接入站队列硬编码为 2048 条，公开配置不能直接缩小。
即使 Linux 入口已限制每包不超过 1500 B，队列最坏正文仍约 2.93 MiB；加上协议/适配层预算和元数据，
当前采用 5 MiB 的保守承诺。实际短测 RSS 远低于该数，但“通常不会填满”不能作为不计入的理由。

修正把这类长期容量预留移到共享全局账户，保持 5 MiB/连接及每 socket 165 MiB backlog 不变。
凭证整个存续期间保持 pending，确保观测到较低 RSS 也不能释放尚可填充的队列额度；
最后释放转为 committed-unconfirmed，继续扣减到下一次物理观测，避免提前承诺分配器仍保留的页面。
新连接仍不能使用控制面和已建立流量的保留额度，request workspace 自身限额也没有改变。
新增回归覆盖容量跨观测保留、释放确认、超额拒绝、保留额度和工作区隔离。

后续仍值得把库的固定队列改成可配置容量或按实际字节准入，以降低每连接最坏预留；
本轮没有修改上游代码、缩小 backlog、提高容器内存或直接移除保护来制造通过。

旧 `a19f6e2` 二进制的[独立内存/并发对照](evidence/h3-admission-local-2026-11-04)
也支持这一方向：2 GiB/32 并发 179/512 成功，4 GiB/32 并发和 2 GiB/2 并发均为 512/512。
这些是两个代理核、开启局部 debug 的诊断，不混入单核、2 GiB 正式性能排名。

另用 `74f5325` 的有界接收二进制，在 4 GiB、32 并发、原有 warn 日志下独立重跑三轮，
1536/1536 请求通过。[完整本地对照](evidence/h3-admission-bounded-local-2026-11-04)
保留所有传输和驱动摘要；manifest 的 `source_revision=3e76164` 是本地驱动 checkout，
实际 Edge/控制器来自上述 `74f5325` artifact。该结果证明提高资源能避开旧子预算，
不作为修正后 2 GiB 的验收，也不混入正式吞吐排名。
