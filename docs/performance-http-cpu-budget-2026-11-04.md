# 用户态/内核态 CPU 差距与 H3 客户端预算

对已有完整节点矩阵重新计算 CPU 账本，无新增压测，也没有把两个 runner 的绝对值拼接成趋势。
原始 [Actions 41757321970](https://github.com/Zelvik-Labs/edge/actions/runs/41757321970) 共 192 格、6,854,656 次成功响应和 128 项 Range 控制，零错误/steal。
使用实际 after `ba474745fae3c08332d9e0862d9d5650550664ff`，四目标独立运行、1 KiB 正文、并发 32、复用连接、每格 5 秒，四轮。
代理/客户端/源站分别分配 1/2/1 个不重叠 CPU；保持基础统计，并未要求竞品实现相同业务统计功能。

## 每个有效请求的 CPU 时间

单位 µs，依次为 **总计 / 用户态 / 内核态**，每列独立取四轮中位。独立中位及内核记账采样不保证严格相加相等。
cgroup 包含代理服务相关进程，不是单个函数计时；不将 gap 全部归于任何库或语言。

|---|---|---|---|
| h1 HIT | 88.48 / 52.52 / 36.21 | 58.47 / 16.34 / 42.20 | 58.42 / 16.15 / 42.36 |
| h1 OFF | 164.00 / 92.51 / 71.61 | 54.41 / 15.08 / 39.30 | 54.86 / 15.30 / 39.50 |
| h1-tls HIT | 107.60 / 66.15 / 41.11 | 69.69 / 31.78 / 37.67 | 67.70 / 29.65 / 37.99 |
| h1-tls OFF | 183.07 / 107.53 / 75.90 | 74.33 / 30.19 / 44.31 | 72.42 / 28.01 / 44.42 |
| h2 HIT | 110.41 / 76.39 / 34.07 | 75.96 / 37.82 / 38.13 | 74.07 / 34.88 / 38.92 |
| h2 OFF | 166.81 / 109.50 / 57.56 | 83.31 / 35.42 / 48.02 | 81.52 / 33.02 / 48.46 |
| h3 HIT | 142.85 / 112.51 / 29.81 | 120.18 / 52.72 / 67.27 | 115.79 / 48.83 / 66.96 |
| h3 OFF | 218.29 / 149.47 / 69.20 | 151.54 / 58.35 / 92.57 | 144.55 / 51.20 / 93.09 |

H1 HIT 中 Edge 用户态约 52.52 µs，对比 Nginx 16.34 µs；内核态反而为 36.21 对 42.20 µs。
H3 HIT 也类似：用户态 112.51 对 52.72 µs，内核态 29.81 对 67.27 µs。
因此，单独削减系统调用或用 XDP/io_uring 绕过内核，不能消除这些 HIT 条件的大部分差距；应优先减少用户态准备、哈希、分配、统计和任务交接的工作。
OFF 条件的用户态与内核态都需要处理，不能从 HIT 结论推断所有条件无需内核优化。
这些是 CPU 预算的定位方向，未独立测出的可回收成本仍未知，也未证明 Tokio 本身不合理。

## H3 观测吞吐受到客户端预算限制

以下也是四轮独立中位，客户端比例除以分配的两核，代理比例除以一核。

| H3 HIT 目标 | 有效 RPS | 客户端两核占用 | 代理单核占用 |
|---|---:|---:|---:|
| Edge after | 6339 | 95.9% | 90.6% |
| Nginx | 6430 | 96.4% | 77.5% |
| OpenResty | 6515 | 97.2% | 75.3% |

客户端已接近两核预算，而竞品代理尚未用满单核；这个窗口不能作为代理饱和容量对比。
Edge RPS 接近竞品并不等于它们的 CPU 效率接近，亦不能把客户端上限误报为服务端上限。
后续 H3 容量实验应先提高客户端生成能力或换到独立更强客户端，并保持相同 TLS、正文和逐响应校验。
增加并发本身不会增加客户端 CPU 预算；也不能只把 CPU/请求倒数写成预测容量，因为调度、内存、并发和批处理会随负载改变。
