[协议诊断](performance-quinn-diagnostic-2026-11-04.md)观察到 OpenSSL 客户端本地发出 10 次 `KEY_UPDATE_ERROR`。
本轮将同一份 C 客户端分别链接同版本 Debian libcurl 的 OpenSSL 与 GnuTLS/ngtcp2 实现，进一步约束故障范围。
第一轮已产生错误及不完整批次；不能认定某一端已修复。

保持原始 Edge/controller 二进制、编译参数、客户端代码、正文、请求数量、QUIC 参数和缓存状态一致。
两个 libcurl 软件包的完整 Debian 版本必须相同，否则在测试前失败；实际客户端及动态库均保留哈希与文件。
OpenSSL/GnuTLS/GnuTLS/OpenSSL 顺序各独立执行 32 KiB HIT、16,384 次 fresh 尝试，共 65,536 次计划尝试。
两种客户端均不启用诊断 trace，错误继续保留并导致工作流失败。

本地已成功编译两种客户端并验证分别加载 OpenSSL 原生 QUIC、GnuTLS + ngtcp2；这只证明构建与后端选择，
不是 H3 网络验证。[Actions 41759827134](https://github.com/Zelvik-Labs/edge/actions/runs/41759827134) 已完成并返回失败，错误和被终止的客户端部分输出均保留。

原始数据与错误归类已核验；仍需从握手确认与密钥切换时序确定违规端及修复方案。
经审批的功能降级：无；不更改生产传输、防护或密钥更新策略。

## 测试 CA 范围控制

下一轮两客户端都显式使用测试 CA 文件，并清除默认系统 CA 目录路径，以排除额外信任目录加载的影响。
此选项仅用于本互操作测试；普通压测客户端默认行为保持。
证书链和主机名校验继续开启，受信任范围更窄；每个实例另用错误 CA 做一次负控制，必须返回 curl 60。
仍用相同请求数量和原期限，若再次超时则继续保留失败，不据部分记录宣称兼容性通过。
系统 CA 目录是否解释主要成本，需要新一轮实测，当前只作为待验证假设。

## 同一 OpenSSL 客户端的组选择控制

增加手动 `groups` 模式：default/X25519/X25519/default，四格均使用同一个 OpenSSL 客户端二进制。
测试 CA、连接数、正文、请求数量和服务端仍固定；仅通过客户端公开选项限制支持组。
该模式开启有界诊断，直接解析 ServerHello 的公开 key_share 组号，按槽记录观察次数与组号变化。
解析器不保存公钥正文、不递归调用 SSL API，字段本身也不作为认证证据。
X25519 格必须实际观察到组号 29，不能仅凭设置参数声称对照生效。

这是受控客户端实验，不改变生产 TLS 默认组或密钥更新策略。握手报文大小与时序仍可能不同，
相关吞吐不参与服务端排名。ServerHello 元数据、截断和组号观察的 C 控制已通过 ASan/UBSan。


[Actions 41764056727](https://github.com/Zelvik-Labs/edge/actions/runs/41764056727) 已完成并核验四格，同一 OpenSSL 客户端实际二进制与动态库哈希完全一致。

| 客户端支持组 | 实际 ServerHello 组号 | 成功 | 错误 | 完整批次 |

| 默认 | 4588（X25519MLKEM768） | 32,754 | 14 | 2/2 |

两种设置各 32,768 次 ServerHello 观察，所有槽的组号没有变化；四项错误 CA 均返回 curl 60，零不完整批次、零基础设施错误。
22 个错误全部保留客户端本地关闭帧：transport code 14、`RX key update again too soon`，无 trace 字节丢弃。
这些 trace 均未记录到关闭前的 HANDSHAKE_DONE；第一次观测 phase=1 的截断包号分别为 10（7 次）、11（9 次）、12（6 次）。
部分 trace 之后还有 phase=1 包；不会把包数当作密钥切换次数。包头回调发生在认证前，不能单凭这些字段判定对端违反协议。

X25519 仍复现相同错误，说明混合组不是必要条件；14 对 8 的短样本也不足以认定改组可解决稳定性问题。
不更改生产默认组或减少密钥更新，后续需要两端可核对的握手确认/包处理证据。
工作流因真实传输错误仍判失败，诊断脚本和离线原始复核通过不能替代流量通过。

## 接收分层的源码线索

进一步审计了上游 OpenSSL 3.5.7 的接收顺序：`ossl_qrx_read_pkt` 在取出首个已解密包前，
会让 `qrx_process_pending_urxl` 处理所有待处理 UDP datagram；通道之后才通过 `ch_rx_handle_packet` 处理帧。
key-update 回调在所审代码中位于 AEAD 验证与 late header 验证成功之后，早于通道处理这些包的帧。
回调的 rxku_allowed 又要求本地 handshake_confirmed；因此存在“后面的更新包已被解包，前面的 HANDSHAKE_DONE 尚未处理”的批次顺序窗口。
这能解释为何 trace 中先出现多个包头，尚无任何 1-RTT 帧，随后就产生错误；仍需要受控网络复现来确认本批次确实经过该窗口。

RFC 9001 §4.1.2 的确认是端点视角：服务端在握手完成时确认，客户端在收到 HANDSHAKE_DONE 时确认；
§6.1 限制的是发起更新的端点。不能把本地尚未确认直接等同于对端没有资格首次更新。
该线索比“GSO 或混合组导致错误”更具体，但目前不据此宣布最终违规方或修复完成。
审计对象是上游源文件，没有逐字核对实际 Debian 构建的全部补丁与内部状态，也未把所有包头都当作已认证包。

[上游片段、完整文件 SHA256/Git blob hash 及 RFC 原文](evidence/quinn-interop-2026-11-04/source-audit/)已固定。
未修改 vendor 或上游，未延迟/禁止生产密钥更新。下一项控制应保持同一服务端和客户端，用受控入站节奏约束待处理批次，再核对错误是否消失。
