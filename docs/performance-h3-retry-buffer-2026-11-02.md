# H3 空结束片段与重试缓冲修复（2026-11-02）

本轮在[接收消融](performance-h3-receive-ablation-2026-11-02.md)中发现独立于批量接收的适配问题，修改请求体过滤器和 H3 重试缓冲。当前继续使用 Quinn / h3；没有引入 tokio-quiche。

**结果：已消除空最终片段造成的逐请求警告，并禁止截断缓冲提供部分正文用于重试。** 匹配诊断中，修复前 10,895 次成功请求产生 10,897 条该警告，修复后 11,741 次成功请求产生 0 条；两边原生错误均为零。411 项相关 Rust 回归、Clippy、诊断构建及修复后 11 项功能场景通过。尚未将这次修复纳入完整发行容量对照，不能据此给出整机提速比例。

## 每请求警告的触发链

启用重试缓冲后，H3 的空缓冲返回 Some(empty)。在已经确认 FIN 的 GET 中，Pingora 将它作为最终正文任务写给 Content-Length: 0 的 H1 源站连接；该连接的正文写入器已经结束，因此逐请求输出“Upstream body is already finished. Nothing to write”。

消融失败场有 22,170 个负载请求及 2 次完整性探针，对应 22,172 条该警告。随后用独立诊断基线复现：10,895 次成功负载请求、0 个原生错误，以及 10,897 条该警告。该现象与业务访问日志开关不同，给无缓存/回源路径增加了实际格式化和写日志工作。

修复位于 [proxy.rs](../src/proxy.rs) 的 request_body_filter：仅当 end_of_stream 为真且片段确实为空时，转为 None 的结束事件。非最终空片段和包含数据的最终片段保持原语义；流量整形仍按原路径执行。错误日志配置没有调整。

没有将所有空重试缓冲直接改为 None：H3 已消费 FIN/trailers 时，is_body_done 可以为真，而 trailers 使 is_body_empty 为假以排除共享缓存。Pingora 此时依赖 Some(empty) 触发初始 body-pipe 结束任务。保留该信号，再规范化最终空片段，可同时保留结束处理与缓存排除。

## 截断重试缓冲

[h3_downstream.rs](../src/h3_downstream.rs) 原实现超过 64 KiB 时只设置截断标记，getter 仍会返回正文前缀，后续较小片段也可能继续积累。完整正文与可重放副本没有严格分开。

现在复用 Pingora H1/H2 已使用的 FixedBuffer，容量仍为 64 KiB。溢出时释放副本并停止继续积累；截断 getter 返回 None，不提供部分正文用于重试。原请求正文继续正常读取，重试缓冲的空结束信号也保留。

新增真实 QUIC 流用例覆盖恰好 64 KiB、再增加 1 字节、后续追加正文、FIN 与缓冲重置；确认完整读取 65,541 字节，同时不暴露不完整重放数据。另一个用例确认 trailers 检测、缓存排除与空结束信号继续存在。公共请求体过滤器用例同时检查非最终空片段、非空最终片段和空最终片段。
