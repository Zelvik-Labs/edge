## 当前实现及 Cloudflare 库的关系

| 层 | 当前依赖 | 职责 |
| --- | --- | --- |
| QUIC / UDP | [Quinn](https://github.com/quinn-rs/quinn) 0.11.11、quinn-proto 0.11.17 | 连接、加密传输、拥塞控制、流量控制、重传和 UDP 收发 |
| HTTP/3 | [Hyperium h3](https://github.com/hyperium/h3) 0.0.8 | HTTP/3 帧、请求流、QPACK 等 HTTP 语义 |
| 适配 | h3-quinn 0.0.10 | 将 h3 的 QUIC 接口接到 Quinn |
| TLS / 运行时 | rustls 0.23.46（aws-lc-rs）、Tokio 1.53.1 | QUIC TLS 1.3、异步 I/O、定时器与任务调度 |
| CDN 请求处理 | 自有 H3DownstreamSession + Pingora 0.9.0 custom session | 路由、共享缓存、WAF、统计及回源 |

生产入口先经过 [quic_udp_demux.rs](../src/quic_udp_demux.rs) 的共享 UDP 分流器，随后由有界通道和自定义 AsyncUdpSocket 交给 Quinn。[http3_proxy_manager.rs](../src/http3_proxy_manager.rs) 为每个 QUIC 连接和每个请求分别运行 Tokio task。下游 H3 请求经 [h3_downstream.rs](../src/h3_downstream.rs) 转为 Pingora 接口；其内部请求头采用 HTTP/1.1 形状，不代表客户端使用 H1。H3 回源另有 [origin_h3.rs](../src/origin_h3.rs) 与连接池；客户端用 H3 不强制源站也用 H3，本轮性能源站为 H1。

Cloudflare 的 [quiche](https://github.com/cloudflare/quiche) 本身实现 QUIC 和 H3，核心 API 由应用驱动收包、发包和定时器；不绑定某个事件循环。[tokio-quiche](https://github.com/cloudflare/quiche/tree/master/tokio-quiche) 是该库的 Tokio 驱动，提供 H3Driver/Controller、socket 集成与任务处理。二者不是两个互斥协议实现，也不是预先确定的快慢版本。Quinn 同样有不依赖 I/O 的 quinn-proto 核心，而当前使用的 Quinn 上层已经集成 Tokio。

本轮没有更换协议栈。缓存旁路位于自有适配/准入层，更换 QUIC 库不会自动补上这一语义。后续若比较 quiche，应保持 TLS 算法、MTU、GSO/GRO、拥塞控制、连接模式和同一 CDN 请求路径；还须实现动态证书、取消、背压、资源准入和 AF_XDP 接口，不能只比较独立 hello-world。

锁定的 h3 0.0.8 发行包 README 明确写着 “still very experimental”，并说明其本身不生成任务、可配合不同运行时。Quinn 与 HTTP/3 层的成熟度应分别评估，不能把这段说明扩展成“Quinn 也处于同一状态”。Cloudflare quiche 的官方说明则列出其在 Cloudflare 边缘网络上的使用。这使 tokio-quiche 值得作为后续候选；当前没有同功能的替换后端或实测性能结论，也没有通过配置关闭 Tokio 的现成开关。

## 缓存根因与修改

旧准入对 `is_http3_downstream` 无条件返回 `ProtocolBodyNotProvenEmpty`。适配器只有在转发读取正文时才知道流结束，不能在缓存查询前证明 GET 的正文为空；GET、缺少 Content-Length 或 Content-Length: 0 都不是可信 FIN。

修改后，准入询问适配器的真实流状态。同步探测只读取已经到达的帧，不等待上传；若提前读到正文或错误，将其保留并交给后续读取，正文计数和重试缓冲不重复累加。`recv_data(None)` 可能表示 trailers，因此还须完成 trailer 校验和流结束确认，含 trailer 的请求继续旁路缓存。尚未收到 FIN 的请求仍保守旁路，不通过提前结束读取来伪造缓存命中。

适配器所有读写方法持有 `&mut self`，改用 Mutex 的 `get_mut()` 取得独占流，无需每次进入异步锁；保留 Mutex 外壳以满足 Pingora 的 Sync 接口。正文改用 Buf 的 `copy_to_bytes`，避免原来强制申请 BytesMut 再复制，也避免对非连续 Buf 使用一次 chunk 后 advance 全部 remaining 的错误。具体 Buf 类型决定是否仍发生复制，不宣称所有路径零复制。

另修正消费 HeaderMap 时忽略重复头后续值的问题，保留全部重复 Cookie/自定义头；标准头名已经规范化，不再为每个头分配小写字符串。删除逐块 ENTER/LOCKED/COMPLETE 调试标记，读取和写入错误仍正常返回。

## 新连接停滞的根因和修复

共享 UDP 分流器在 Normal 压力下对每个源 IP 设置了 **128 条新路由 / 10 秒**窗口；Elevated/High/Critical 分别为 32/8/2。两路客户端经 Docker 使用相同源 IP，各到约 64 个连接时触发窗口。256 请求的旧版诊断中，192 成功、64 个握手超时；2048 请求批次在 90 秒执行上限内无法完成。窗口限制同时发生在分片 ClientHello 重组与新路由准入，Quinn 尚未看到这些 Initial，因此只查看 H3 manager 的连接准入日志找不到拒绝。

客户端系统调用证明确实发送并在约 1/3 秒重传 Initial，但未收到回复。容器内网直连仍能复现，排除了仅由 Docker 发布端口造成的解释。服务端诊断未见 UDP RcvbufErrors/SndbufErrors/InErrors，Quinn endpoint 也没有对应的解码失败。这些诊断有额外开销，均不计入容量结果。

对仅提供本机 H3、没有普通 UDP 或 QUIC 透传配置的端口，Normal 压力时直接建立 H3 路由并交给 Quinn 验证协议，省去重复解密 ClientHello、重组和通用路由 IP 窗口计费。配置判定在同一个读锁快照内同时检查两种转发索引，已有路由、CID 及热更后的混合端口路径仍保留。

**保护取舍明确：** 这类端口正常压力下不再使用 128/10 秒的通用分流窗口；仍保留源 IP 封禁、全局路由容量、有界队列和字节预算、Quinn 协议验证与抗放大、原 Retry 策略、连接/请求资源准入。压力升高和混合转发端口继续使用原有窗口。新增 NAT 回归覆盖同 IP 的 256 个路由、无额外 ClientHello 重组状态，以及队列溢出和字节归还。该调整不是无限制接受连接；真实攻击负载和长时间路由回收仍需额外验收。

## 范围边界

共享云的 CPU steal 和后台控制端告警仍会影响数值；短测不代表 24/72 小时稳定性。存储格式、基础统计、TLS 证书校验及现有超时保留；本机 H3 正常压力下的路由窗口调整已在上文明确。H2/长冷缓存回退与 ENOSPC 隔离不属于本轮已修复项目；没有部署或发布。

性能仍受共享 UDP 路径限制：每包 recv_from、数据复制、队列同步和自定义 socket 发包仍存在，当前内核路径没有完整使用 Quinn 原生 UDP 的批收发/ECN/GSO/GRO 能力。之后若改为原生专用 socket，需要同时处理混合端口、配置切换、CID/迁移、资源保护和 AF_XDP；换成 quiche 同样不能自动消除这些自有链路成本。

H3 分流路由仍按活动时间回收，Normal 空闲超时为 180 秒，并未与每个 QUIC 连接的关闭立即绑定。持续大量新连接时，历史路由累计仍可能提高路由占用并触发压力保护；本轮有界新连接批次不等于已经解决持续 churn 的生命周期管理。上游固定 H1，本轮也未验收 H3 回源连接池与热更负载。
